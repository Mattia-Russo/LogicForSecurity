# LogicForSecurity

This repository contains a set of protocol models and security analyses developed for a course on logic and security. The project focuses on formal modeling of authentication and secrecy properties using the AnB language and the OFMC model checker.

## Overview

The repository includes several protocol variants organized by week (`w2`, `w3`, `w4`, `w5`, `w6`), each containing:

- `.AnB` protocol specifications
- diagnostic output files
- attack reports generated by OFMC
- examples and excluded variants used to test protocol behavior

The goal is to model communication protocols, define the intended security goals, and check whether attacks exist under adversarial assumptions.

## Repository structure

- `protocol-project.pdf` — project documentation or assignment description
- `w2/` — Week 2 protocol models and attack analysis
- `w3/` — Week 3 protocol refinements and attack detection
- `w4/` — Week 4 models and key lookup variant
- `w5/` — Week 5 models and further protocol analysis
- `w6/` — Week 6 protocol specification

## What the models represent

The `.AnB` files describe communication protocols between agents such as:

- `A` (client or initiator)
- `P` (proxy or intermediary)
- `B` (server or resource owner)

The files define:

- agents and identities
- cryptographic keys and functions
- protocol steps and messages
- security goals such as secrecy and authentication

For example, the Week 2 model includes a protocol where `P` requests access to `photos(A)` at `B`, and the security goals validate whether the photos remain secret and whether the different parties authenticate each other correctly.

## Security analysis workflow

The workflow is typical of protocol verification with model checkers:

1. Define the protocol in AnB syntax.
2. Specify the initial knowledge of each agent.
3. Add security goals such as secrecy and authentication.
4. Run OFMC to search for attacks.
5. Examine the attack trace and revise the protocol model.

The files in `attack found` logs highlight exactly this process: the model checker identifies violations and provides trace evidence showing how the attacker can exploit the protocol.

## Example interpretation

A typical issue seen in the logs is that a value intended to remain secret is treated too broadly or modeled incorrectly as a plain constant, which leads the model checker to report an attack. These traces are then used to refine the protocol and correct the formal specification.

This is a good example of how formal protocol verification helps uncover subtle flaws before deployment.

## Tools used

This project is centered around formal methods for security protocol analysis, particularly:

- AnB protocol specification language
- OFMC model checker
- security notions including secrecy and authentication

- Several folders contain variants that were intentionally tested, excluded, or refined over multiple weeks.
